# Terraform: the Azure Setup as Code (Week 10)

Until Week 9, everything on Azure had been created with individual `az` commands. That is hard to repeat, easy to get wrong, and only documented in prose. Since Week 10, the setup is described in **Terraform** files in [infrastructure/](../infrastructure/). Terraform compares those files with what really exists in Azure and makes only the changes needed. The runbook is [infrastructure/README.md](../infrastructure/README.md).

## Key ideas
| Idea | Meaning | In this project |
| --- | --- | --- |
| **Infrastructure as Code (IaC)** | Infrastructure is described in files that are version-controlled, reviewed and re-run | `infrastructure/foundation/*.tf`, `infrastructure/app/*.tf` |
| **Declarative** | You describe *what* should exist; Terraform works out *how* to get there | e.g. "a Linux web app on F1 running this image" |
| **Provider** | A plug-in that talks to one platform's API | `hashicorp/azurerm` **5.8.0** and `hashicorp/random` 3.9.1, pinned exactly; `.terraform.lock.hcl` pins the builds |
| **Resource** | One thing Terraform manages | `azurerm_postgresql_flexible_server.main` |
| **Variable / output** | Inputs to a configuration / values it publishes | `name_suffix`, `plan_sku` / `postgres_fqdn`, `app_database_url` |
| **State** | Terraform's record of which real object belongs to which resource in the code | `terraform.tfstate`, **local and git-ignored** (owner's choice) |
| **`plan` / `apply` / `destroy`** | Preview changes, make them, delete everything in this configuration | Always read the plan before applying |
| **`import` block** | "This existing object is that resource in my code." Adopts it without recreating it. | Used once to adopt everything built by hand in Weeks 7–9 |
| **`prevent_destroy`** | Terraform refuses any plan that would delete the resource | Registry, PostgreSQL, storage, resource group |

## Two layers (owner's decision)
```text
foundation/  (LOCKED: prevent_destroy)                 app/  (destroy and rebuild freely)
  resource group, budget                                 App Service plan (F1) + web app
  container registry  ──── registry_id ──────────────►   AcrPull role for the web app identity
  PostgreSQL + db ecom ──── server_id, fqdn, ─────────►  31 firewall rules (one per outbound IP)
                            app_database_url                app settings (DATABASE_URL, ...)
  storage + container ──── container_id, url ─────────►  Blob Data Contributor role
  random passwords (admin, ecom_app)                     random SECRET_KEY
```
- **Why two layers:** `terraform destroy` stops with an error if *any* resource in the configuration has `prevent_destroy`. A single configuration could therefore never be destroyed at all, and the parts holding data or images must never be destroyed.
- **The app layer reads the foundation's outputs** through `data "terraform_remote_state"`, pointed at the foundation's local state file.
- **Verified:** `terraform plan -destroy` on the foundation fails with *"Instance cannot be destroyed: azurerm_container_registry.main has lifecycle.prevent_destroy set"*.

## Design decisions
- **Adopt, don't rebuild.** `import` blocks brought the live resources under Terraform without touching data, images or the owner's admin account. The code was adjusted until `plan` showed only the intended changes, and then **"No changes"**.
  - The foundation's import blocks are kept as documentation. Those resources never disappear, so the blocks stay harmless.
  - The app layer's import file was **deleted after adoption**. Once the app layer can be destroyed, import blocks pointing at objects that no longer exist would make Terraform fail.
- **Firewall rules come from the app itself:** `for_each = toset(azurerm_linux_web_app.api.possible_outbound_ip_address_list)`. If the app's addresses change, the next `apply` updates the rules, so the manual "31 rules must match" check from Week 8 is gone.
  - **The catch ("unknown until apply"):** for a brand-new web app, Terraform cannot know these addresses at plan time. A rebuild therefore applies the web app first (`-target`), then everything else.
- **Secrets are generated by Terraform** (`random_password`): the PostgreSQL admin password, the `ecom_app` password and the app's `SECRET_KEY`.
  - A rebuild needs no hand-made secrets.
  - **The state file therefore contains secrets.** That's why it stays local, git-ignored and backed up privately, and why outputs holding secrets are marked `sensitive`.
  - azurerm 5.x also offers *write-only* arguments (`administrator_password_wo`) that are never stored in state. That's a good next step if the state ever has to be shared.
- **The database user `ecom_app` is not a Terraform resource.** Roles inside PostgreSQL are set by `scripts/create_app_db_user.py`, using the Terraform outputs. A PostgreSQL Terraform provider would also need direct network access to the server, so it was left out to keep things simple.
- **Deployments are not Terraform's job.** The web app has `ignore_changes` on its image tag. Terraform sets the image only when it *creates* the app; later deployments (by hand now, GitHub Actions from Week 11) change it without the next `apply` rolling them back.
- **Plan size is a variable** (`plan_sku`, default `F1`). A temporary, approved B1 is `-var plan_sku=B1`, and going back is a plain `apply`. The code always shows the intended state.
- **Budget amount = the hard cap (₹5,000).** Terraform requires whole-number alert percentages. 10/20/50/80 % of ₹5,000 give exactly the ₹500 / ₹1,000 / ₹2,500 / ₹4,000 alerts from Week 7, plus a forecast alert at 80 %.

## Problems found while adopting (and the fixes)
| Problem | Cause | Fix |
| --- | --- | --- |
| `Attribute must be a whole number, got 12.5` | Budget thresholds must be integers | Budget amount ₹5,000 with 10/20/50/80 %: the same rupee alerts |
| The plan would have **re-enabled FTP and WebDeploy basic-auth publishing** | The provider's default for `ftp_publish_basic_authentication_enabled` / `webdeploy_…` is `true` | Both set to `false` explicitly. **Lesson: read every changed line of a plan.** |
| **The first app plan printed the live `DATABASE_URL` and `SECRET_KEY`** | Plans show the *old* values of attributes Azure doesn't mark as secret (`app_settings`) | Both were rotated by that same apply. **The old `ecom_app` password was verified as rejected.** The plan text was deleted. Since adoption, state marks the settings as sensitive. |
| **App down after the apply ("web app is stopped")** | Import stored the image as `<registry>/ecom-api:<tag>`. With `docker_registry_url` also set, Azure combined them into `<registry>/<registry>/ecom-api:<tag>`, which doesn't exist. The container couldn't start, and the restarts used up the F1 daily quota. `ignore_changes` on the image hid the problem from `plan`. | Image name set once to `ecom-api:<tag>` (with `ignore_changes` briefly lifted), then restored. **Lesson: check the effective value in Azure after importing, not only the plan.** |
| The apply took about 33 minutes and the app restarted early | Changing app settings restarts the app at the start of the apply, while 31 firewall rules are created slowly | Rebuilds now apply the web app first, the rules second, and restart at the end |

## Adoption results
- **Foundation:** 7 imported, 2 added (passwords), 5 changed in place (tags, admin password, budget, explicit storage network setting), **0 destroyed** → then **"No changes"**.
- **App:** 4 imported, 32 added (31 firewall rules + `SECRET_KEY`), 2 changed in place, **0 destroyed** → then **"No changes"**.
- The live app connects as `ecom_app` over TLS 1.3 using the Terraform-generated password, and the old (exposed) password is rejected. The 31 hand-made firewall rules were deleted after Terraform's replaced them.

## Destroy and rebuild drill
Done on 2026-10-20, on a temporarily approved B1 plan so the F1 quota couldn't interrupt it:

| Step | Command | Result | Time |
| --- | --- | --- | --- |
| Safety check | `terraform plan -destroy` (foundation) | **Refused:** "Instance cannot be destroyed … prevent_destroy" | seconds |
| Destroy | `terraform destroy` (app) | 36 destroyed: plan, web app, 2 roles, 31 firewall rules, `SECRET_KEY`. The public URL stopped answering. | 32 min |
| Foundation intact? | `az` checks + a database query | Registry (5 image tags), PostgreSQL and storage unchanged; **the owner's admin account and migration level `85737df2c161` still there** | — |
| Rebuild 1 | `apply -target=azurerm_linux_web_app.api` | Plan, web app, new `SECRET_KEY` | 1.4 min |
| Rebuild 2 | `apply` | 2 roles, 31 firewall rules (from the new app's outbound IPs) | 33 min |
| Start | `az webapp restart` | `/health/ready` OK; **smoke test 10/10** | 1.1 min |
| Back to F1 | `apply` (default `plan_sku`) | Smoke test 10/10 once warm. The first request or two after the switch got a 503 while the container started. | — |

Afterwards, **both layers report "No changes"**, and the 31 firewall rules match the rebuilt app's outbound IPs exactly.

**Takeaways:**
- The rebuild needs no manual steps or secrets, and data survives because it lives in the locked layer.
- Most of the time is spent on firewall rules, which Azure PostgreSQL changes one at a time.
- A rebuilt app gets a new `SECRET_KEY`, so everyone logs in again.

B1 was used from 16:42 to 17:55 UTC (1.2 h): about ₹2.11, at most ₹3.46 if billed per started hour.
